## 1. Cluster / Finding ごとの判断

### Cluster `plugin:vercel` — F-001〜F-004

**現時点では変更を提案しない。人間の意図確認が先。**

| Finding | 対象 | 判断 | 理由 |
|---|---|---|---|
| F-001 | `vercel:react-best-practices` | 保留 | Claude Code では未導入、Codex では無効だが、その状態が意図的か不明。実際に参照された記録もない |
| F-002 | `vercel:nextjs` | 保留 | 同上 |
| F-003 | `vercel:verification` | 保留 | 同上。Andy、Claire、Codex の常時指示から参照されているが、実害は未測定 |
| F-004 | `vercel` 名前空間の第4参照 | 保留 | 同じ root cause。対象を利用可能にしたいか判断できない |

利用する意図が確認できた場合のみ、次の手順を提案する。

1. 必要な4参照が、実際に対象プラグインへ含まれることを確認する。
2. Claude Code、Codex、または両方のどこで必要か決める。
3. 対象ランタイムだけにインストール／有効化する変更案を作る。
4. `~/.codex/AGENTS.md` など protected resource は、必要な参照部分だけを対象にレビューする。
5. 次回起動セッションで各参照が解決することを確認する。実行中セッションには反映されない。

利用しない意図なら、インストールではなく参照を削除または説明文へ変更する差分を、関連コピー間でまとめてレビューする。ただし、この選択も人間の回答前には提案しない。

10件を同一内容へ機械的に統一する根拠はない。特に F-012〜F-014 は、差分自体が正しい可能性がある。

同一化する方針が確認された場合のレビュー手順は次のとおり。

1. スキルごとに「共通本文」と「runtime 固有部分」を分類する。
2. 正本の保存場所と同期方向を決める。
3. runtime 名、参照する指示ファイル名、利用可能なツール名は固有部分として維持する。
4. 意味上共通であるべき本文だけの差分案を作る。
5. 次回起動した Claude Code と Codex の双方で discovery と内容を確認する。

mtime が新しい側を自動的に正本とする提案はしない。レポート自身も、mtime は正しさを示さないとしている。

### F-015 — `superpowers:test-driven-development`

**現時点では変更を提案しない。**

未知の名前空間であり、本当にスキル参照なのか、移植元に残った名称なのか、単なるラベルなのか判断できない。また、どちらの runtime で必要かも不明。

ライブ参照だと確認できた場合は、次の順序でレビューする。

1. 対象スキル／プラグインの正式名称と提供元を確認する。
2. Claude Code と Codex のどちらで必要か決める。
3. 導入案、または既存の同等スキルへの参照変更案を比較する。
4. 両方の `systematic-debugging` コピーを同時にレビューする。
5. 次回起動セッションで解決を確認する。

ライブ参照でない場合は、誤認されない通常文へ書き換える差分を検討する。

### F-016 — `ctrl:despawn`

**変更を提案しない。**

引用された文脈では、これはプラグインやスキル名ではなく、エージェント間で送る「制御メッセージの種別」に見える。`ns:name` 形式だけを根拠に missing target と判定した可能性が高く、レポート内の証拠からは修正対象とは認めにくい。

むしろ doctor 側で、コード記法中のプロトコル名やメッセージ種別をスキル参照から除外できるか検討する余地がある。ただし、このレポートだけでは doctor の修正仕様までは決められない。

## 3. レポートだけでは判断できなかったこと

最も不足しているのは、**設定の意図、実行時の事実、正本の所在**である。

- `vercel` を無効化した理由。
- `vercel` プラグインの実際の内容と、F-001〜F-004 の名前が本当に提供されるか。
- 各参照が実行時に解決を試みられ、失敗しているか。
- 失敗している場合のユーザー影響、頻度、エラーログ。
- Claude Code と Codex のどちらで各機能が必要か。
- F-004 の具体的な利用意図。
- drift している10スキルの正本、所有者、同期ポリシー。
- F-005〜F-010の差分が意図的か、それぞれ何を意味するか。
- Codex 側に invocation 記録がない理由。未使用なのか、計測非対応なのかを区別できない。
- `superpowers:test-driven-development` の提供元、正式名称、過去の導入履歴。
- `ctrl:despawn` がプロトコル値であることを裏づける仕様。
- 起動中セッションの実測結果。
- 親ディレクトリから継承される Claude Code の指示。
- Codex の `AGENTS.override.md`、階層連結、`project_doc_max_bytes` の影響。
- `<project>/.codex` 以下、inline hooks、plugin 同梱 hooks、hook trust 状態。
- shell、launchd、cron、および指定されなかった launcher の影響。
- MCP サーバーへの実接続可否。
- 複数 `CODEX_HOME` が存在する場合の差。
- rules DSL の実際の意味と有効性。
- snapshot 後に環境が変更されていないか。
- 修正後の検証方法・期待結果・ロールバック方法。
- インストールや有効化に伴うセキュリティ、権限、ネットワーク、費用上の影響。

したがって、「参照文字列が見つからない」「同名ファイルが異なる」という静的事実までは分かるが、「どちらをどう直すべきか」には届いていない。

## 4. 特定の直し方への誘導・評価語

### 誘導性がある箇所

- `ERROR`、`UNREACHABLE_REFERENCE`、`missing_target` という名称は、実害未確認でも「導入または修正が必須」と受け取らせやすい。
- `plugin:vercel` として4件をまとめた構造は、プラグイン有効化を自然な解決策として想起させる。ただし本文では、参照削除と導入のどちらとも結論していない。
- `CROSS_RUNTIME_DRIFT` は、差分を不整合として揃える方向へ誘導しやすい。実際には F-012〜F-014 のように runtime 固有差分である可能性がある。
- 差分表示で Codex 側を `+` として示しているため、新しい側を採用すべき印象を生み得る。ただし、レポートはmtimeが正しさを示さないと明記している。
- `ctrl:despawn` を `missing_target` と分類したこと自体が、コロン形式を参照とみなす実装上の偏りを示している。

### 評価語

レポートは「unused」「unnecessary」「bloat」「waste」「cleanup candidates」に相当する判断を避けるよう明示しており、個々の資源を「不要」「無駄」と評価してはいない。

一方で、以下は実質的な評価ラベルである。

- `ERROR`
- `WARN`
- `UNREACHABLE_REFERENCE`
- `missing_target`
- `CROSS_RUNTIME_DRIFT`
- `not_installed`
- `disabled`
- `discovered=false`
- `load_mode=never`

これらは観測を整理するうえでは有用だが、とくに `ERROR` は「severity は runtime impact を示さない」という注記と直感的に衝突する。

## 5. 妥当な修正判断まで辿れるか

**2 / 5**

静的な所在、参照箇所、差分、調査範囲、未確認事項は丁寧に提示されており、追加確認の入口としては有用である。一方、修正判断に不可欠な意図、正本、実行時影響、プラグイン内容、利用 runtime が欠けている。

このレポートだけで安全に判断できるのは、F-016を「修正しない寄り」と評価すること、および no-finding guards に手を出さないことまで。F-001〜F-015について具体的な変更を確定するには、人間への確認と、レポート外の実測・仕様確認が必要である。
